**Can this check ever go red?**

A check that cannot fail is worse than no check, because it is read as
evidence. This tool audits the *check*, not the code the check is pointed at.

You give it a **claim** — one check command, paired with the source it says it
verifies — and it answers in one of four words:

| Verdict | Meaning |
|---|---|
| `DISCRIMINATING` | every behaviour-changing mutation of the claimed region turned the check red |
| `WEAK` | some did, and named survivors remain: the check accepts specific wrong implementations |
| `VACUOUS` | nothing did. Green from this check is not evidence for this claim |
| `INCONCLUSIVE` | the audit could not reach a conclusion. Never reported as a pass |

---

## Why

When one agent writes a change *and* the test that verifies it, the test very
often cannot fail. `assert result is not None` passes for every implementation
that returns an object. An assertion inside `try: ... except: pass` passes for
all of them. A suite that collects zero tests exits green. A reviewer sees a
green tick and approves, and the tick meant nothing.

This is not hypothetical and it is not rare. It is the specific failure mode of
AI-assisted code review, and it is invisible to every tool that only asks
*did the suite pass?*

## What it does

Four stages, in this order, because the order is load-bearing.

**1. Green-baseline guard** (`baseline.py`). Before any mutation, the unmutated
tree must be green — and "green" is checked properly. pytest exits **5** when it
collected zero tests and **4** on a usage error; in both cases nothing ran, and
a mutation campaign layered on top scores 100% for free. A run also fails the
guard on `INTERNALERROR`, on `collected 0 items`, and on timeout. A non-green
baseline short-circuits the claim to `INCONCLUSIVE` and no mutants are run.

**2. Static vacuity scan** (`static_scan.py`). AST patterns that make a check
unable to go red: `no_assertion`, `empty_body`, `constant_assertion`,
`self_comparison`, `presence_only`, `swallowed_assertion`, `unconditional_skip`.
These are **candidates, never verdicts** — `assert x is not None` is vacuous
when the callee always returns an object and load-bearing when it can return
`None`, and the test file does not say which. They locate; stage 3 decides.

**3. Mutation as a negative control** (`mutants.py`, `audit.py`). Mutants are
generated by rewriting the AST and unparsing, so every mutant is valid Python —
a mutant that merely fails to parse is killed by any check, vacuous ones
included, and would inflate the score for nothing. Docstrings and
exception/logging message strings are excluded for the mirror-image reason:
they change no behaviour, survive every honest suite, and would brand correct
checks `VACUOUS`. Mutation is scoped to the claim's own file and optional line
range, so a check is never credited for killing something it does not claim.

**4. Two guards on the result.** A mutant that stops the check from *running*
— import error, collection failure, usage error — looks exactly like a kill
from outside. Those runs are counted separately and excluded from both the
numerator and the denominator. And each mutant runs in a sandbox that
**refuses to be an existing directory**: copying a tree into a path that already
exists nests it one level deeper, the check then reads the stale copy, and every
mutant is reported killed.

## Install and run

```bash
git clone https://github.com/jianwang-ntu/ibm-bob-2-hackathon
cd ibm-bob-2-hackathon
pip install -e .

vacuity-audit scan  --root .                      # static candidates, no execution
vacuity-audit audit --root . --spec vacuity.toml  # the full audit
```

Exit codes: `0` all discriminating · `1` any vacuous · `2` any inconclusive ·
`3` any weak. Each band is separate on purpose — "not evidence", "could not
tell" and "evidence with gaps" call for three different actions.

## Try it on the worked example

`examples/demo_project` is a four-line pricing function with two test files.
Both are green. One checks values, one checks that a value came back.

```bash
cd examples/demo_project
vacuity-audit audit --root . --spec vacuity.toml
```

Measured, with 12 mutants per claim:

```
real_suite_verifies_pricing     WEAK   8/9
vacuous_suite_verifies_pricing  WEAK   2/9
```

Both are `WEAK` rather than one being clean, and that is the honest answer: the
"real" suite never tests a 0% discount, so a mutant that moves the guard from
`percent < 0` to `percent < 1` survives it. The tool found a genuine gap in the
test the author of this repo believed was complete. The 8/9-versus-2/9 split,
and the named survivors, are the signal — not a single pass/fail letter.

## It audits itself

`vacuity.toml` in this repo points five checks at the five modules they claim to
verify. Current result, reproducible with the command above:

| claim | verdict | killed |
|---|---|---|
| `baseline_guard_reads_baseline` | WEAK | 3/8 |
| `static_scan_tests_read_static_scan` | WEAK | 7/10 |
| `runner_tests_read_the_isolation_code` | WEAK | 7/10 |
| `mutant_tests_read_the_operators` | WEAK | 9/10 |
| `report_tests_read_the_exit_codes` | WEAK | 8/10 |

Nothing here is `DISCRIMINATING`. That is a real finding about this repository's
own tests, it is stated rather than hidden, and the survivors are listed in
`evidence/self_audit.json`. `baseline_guard_reads_baseline` scores worst because
its tests match reason strings by substring, so appending to one does not turn
them red — a gap the tool found in its own suite.

The static scan also flags four of this repo's own tests as vacuity candidates,
including one `no_assertion` that is a true positive: `test_every_mutant_is_valid_python`
relies on `ast.parse` raising rather than asserting.

## Two design changes that came from running it

Both are recorded because they are the kind of thing a README normally hides.

1. **The fourth verdict.** The first design had three, and any surviving mutant
   made a claim `VACUOUS`. Run on the example, the honest suite killed 8 of 10
   and the deliberately vacuous one killed 2, and the rule called both `VACUOUS`.
   That answered a different question from the one on the tin — a check that
   kills 8 of 10 obviously *can* go red. `WEAK` exists because the measurement
   contradicted the design.

2. **One denominator.** The report printed `3/10` next to a sentence reading
   "3 of 8", because `mutants_applied` counted runs where the check never
   executed. A kill rate over a denominator the numerator was never measured
   against is the same class of error this tool exists to find.

## What is NOT built

Stated plainly, because an honest smaller tool beats an inflated description of
a larger one.

- **IBM Bob 2.0 has not been used on this repository.** The hackathon runs
  2026-09-25 to 2026-09-27 and access is granted at the start; this code was
  written before it, under the event page's own invitation to "get a head start
  on your project". No Bob-assisted code and no Bob session screenshots exist
  yet, and none are claimed.
- **Oracle sensitivity is not implemented.** Swapping a check's *input* for
  noise to see whether the verdict moves at all is designed and described here,
  and there is no code for it. It is not counted in any number above.
- **Python only.** The AST operators and the pytest exit-code semantics are
  Python-specific. Nothing here reads another language.
- **No CI integration, no diff-scoping, no incremental mode.** Every audit is a
  full run of the claims you give it.
- **The verdict depends on the mutant budget, and the tool does not warn you.**
  `--max-mutants` caps the pool, and the cap is taken in generation order, not
  by sampling. Measured on the same example: at `--max-mutants 4` the real suite
  reports `DISCRIMINATING 4/4`; at `12` it reports `WEAK 8/9`. A small budget
  can therefore turn a gap into a clean bill of health. Treat `DISCRIMINATING`
  at a low budget as "no counterexample found yet", not as "none exists".
- Of the four judging-criteria artifacts a lablab submission needs, the
  **slide deck** and the **cover image** exist —
  `submission/slides/evidence/slides_presentation.pdf` and
  `submission/cover/evidence/cover_image.png`, both generated from
  `evidence/*.json` and checked against their own shipped bytes.
  **The demo video and the demo URL do not exist in this repository.**
  Both need hosting accounts this entry does not hold.

## Prior art

Mutation testing is decades old, and `mutmut`, `cosmic-ray` and Pitest do the
mutation part better than this does. The delta is what the mutation is *for*:
those tools score a suite's overall quality, this one answers a **per-claim**
question — does *this* check read *this* module — and pairs it with the
baseline guard, the did-not-run exclusion and the sandbox-nesting refusal,
which is where the false 100% scores actually come from.
